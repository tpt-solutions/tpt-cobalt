1. Executive Summary
TPT Cobalt is the unifying workspace that transforms TPT Solutions' existing nine-pillar Rust ecosystem into a single, coherent, PyTorch-replacing computational substrate.
The modern AI/ML stack (Python + PyTorch + C++/CUDA) is a bloated, long-winded farce of overlapping abstractions, GIL contention, and fragile FFI boundaries. TPT Cobalt eliminates this farce by:
Forking the nine existing pillar repositories into a single workspace as first-party crates, free to diverge and be optimized for Cobalt's unified tensor/autograd requirements.
Building five targeted glue crates (tpt-tensor, tpt-autograd, tpt-ml, tpt-hub, tpt-runtime) starting from pre-existing implementations in tpt-rust6 rather than from scratch.
Defining the language runtime, tooling, and system layer that complete the computational substrate.
Enforcing strict dependency flow so the entire stack shares a single Tensor type, a single autograd tape, and a single execution runtime.
Keeping both lines alive: The original tpt-solutions/* repos remain independently maintained standalone products. Cobalt's forked copies are optimized for the unified stack. Two product lines by design.
The result is a framework where a neural network, a finite-element solver, a quantum simulator, and a photonic accelerator compiler all speak the same language — with compile-time unit safety, formal verification, and zero Python in the critical path.
2. Core Design Principles
These principles are non-negotiable. Any architectural decision that violates them must be rejected.
Forked & Optimized, Not Shared. Cobalt copies the nine pillar repos into its own workspace as independent, first-party crates, free to diverge and be optimized for Cobalt's needs (shared tensor type, shared autograd tape, GPU-first layouts, etc.). The original nine repos remain live and independently maintained for standalone use — they are a separate product line, not a dependency Cobalt tracks. There are now two lines of each pillar by design: the standalone repo, and the Cobalt-internal fork. They are allowed to drift apart.
Single Tensor Type. Every layer — from tpt-math matrices to tpt-physics FEA fields to tpt-gpu LLM inference — operates on the same tpt-tensor::Tensor.
Single Autograd Tape. Neural nets, ODE solvers, FEA, and DEM share the same reverse-mode gradient tape. Differentiate through reality, not just x @ w + b.
Compile-Time Unit Safety. Dimension mismatches are rejected by the compiler, not discovered at runtime.
Formal Verification by Default. tpt-telos proves memory bounds and invariant preservation across the entire stack.
Hardware Agnosticism. A model written once compiles to GPU, FPGA, photonic mesh, neuromorphic chip, or MCU swarm via tpt-crucible.
No GIL, No CPython, No PyO3 in the Critical Path. Python is an optional ingestion format (via Catalyst), never a runtime dependency.
Functional Core, Dynamic Surface. The engine is pure and immutable; the scripting surface is ergonomic and mutable.
First-Class Tensors in the Runtime. Tensors are native values in the language runtime, not boxed afterthoughts. The Value enum has a dedicated Tensor variant with zero indirection.
Eager by Default, Compiled When It Matters. The REPL and notebooks execute eagerly for fast iteration. The @compile decorator traces and optimizes hot paths. No forced graph mode.
3. Repo Strategy — Fork, Optimize, Keep Both Lines Alive
Why a clean fork beats git dependencies here
The alternative (treating the 9 repos as external git dependencies pinned in Cargo.toml, kept "unmodified") works fine until a glue crate needs to change something upstream of a pillar's public API — which Phase 3 explicitly requires (tpt-physics and tpt-science need to consume tpt-tensor internally, not just at their boundary). At that point you have three bad options with git deps:
Fork silently and diverge (defeats the point of tracking upstream)
Upstream every change and wait on 9 separate repos to cut releases before Cobalt can build
Pin to a commit hash and accept the repos are already forked in practice, just without saying so
The decision: fork openly, optimize freely inside Cobalt, and let the standalone repos keep shipping independently for people who just want tpt-fem or tpt-physics on their own. Two maintained lines instead of one canonical one — more honest about what's actually happening than a git dependency pretending nothing changed, and it doesn't force standalone users onto Cobalt's release cadence or its GPU-tensor-shaped opinions.
One-way fork — no sync policy needed
Since the fork is one-way (Cobalt's copies and the standalone repos have independent cadences, full stop), there's no ongoing cherry-pick process to design or staff. UPSTREAM.md still records the fork-point commit per crate — useful provenance, and a starting point if anyone ever wants to diff how far things have drifted — but it's a historical marker, not a queue of pending merges. If a specific upstream fix is ever worth pulling into Cobalt, that's a deliberate one-off decision made at the time, not a scheduled process.

5. The Five New Glue Crates (Built in Cobalt, Starting from tpt-rust6)
These are the only new code written in the Cobalt umbrella. They provide the missing unifying abstractions, starting from pre-existing implementations in tpt-rust6 rather than from scratch.
5.1. tpt-tensor — The Universal Tensor
Starting point: tpt-rust6::tpt-omni (Arrow-backed unified layout, zero-copy views — already implemented)
A single, device-agnostic, zero-copy tensor type that every other crate consumes.

pub struct Tensor {
    pub(crate) meta: TensorMeta,
    pub(crate) storage: Arc<dyn Storage>,
    pub(crate) autograd: Option<Arc<AutogradNode>>,
}

pub struct TensorMeta {
    pub shape: Shape,
    pub strides: Strides,
    pub dtype: DType,
    pub device: Device,
    pub layout: Layout,
    pub version: u64,  // for in-place mutation tracking in autograd
}

pub trait Storage: Send + Sync {
    fn device(&self) -> Device;
    fn dtype(&self) -> DType;
    fn byte_len(&self) -> usize;
    fn as_bytes(&self) -> &[u8];
}

Key features:
Zero-copy views (reshape, transpose, slice only modify metadata)
Copy-on-write storage via Arc
Bridges tpt-math-linalg (CPU math) with tpt-gpu-primitives (GPU kernels) and tpt-crucible (exotic hardware)
First-class citizen in tpt-gpu-script
Arrow-backed for zero-copy interop with data loaders
5.2. tpt-autograd — The Tensor-Graph Tape
Starting point: tpt-rust6::tpt-grad (proc-macro autograd, compile-time gradient emission — already implemented)
A tensor-aware reverse-mode autodiff engine built on tpt-math-autodiff-rev.
Responsibilities:
Dynamic (eager) and traced (compiled) graph execution
Vector-Jacobian Product (VJP) registration for custom ops (including tpt-physics solvers)
Gradient checkpointing (activation recomputation for VRAM-constrained training)
Cross-device gradient accumulation
In-place mutation versioning (invalidates tape on illegal mutation)
Why this matters: tpt-physics-ai currently exposes differentiable state, but there is no unified tape shared with neural networks. tpt-autograd makes it possible to backpropagate through an FEA solve and a transformer layer in the same graph.
5.3. tpt-ml — The Standard ML API
Starting point: tpt-rust6::tpt-learn (high-level ML training, compile-time shape verification — already implemented)
The bread-and-butter of modern AI.
Contents:
nn: Linear, Conv1d/2d/3d, LayerNorm, BatchNorm, Embedding, MultiHeadAttention, TransformerBlock, Module trait, parameter initialization
optim: SGD, AdamW, learning rate schedulers
loss: MSE, CrossEntropy, NLL, Huber, BCE
data: Dataset trait, DataLoader (multi-threaded, Arrow-backed), standard transforms
Depends on: tpt-tensor, tpt-autograd, tpt-math-linalg
5.4. tpt-hub — Model Loading & Interop
Starting point: tpt-rust6::tpt-io (universal format reader: CSV/JSON/Parquet/Arrow-IPC/HDF5 — already implemented) + tpt-crucible's Catalyst for the ONNX/GGUF/SafeTensors ingestion paths tpt-io doesn't cover
Seamless ingestion of the world's existing model ecosystem.
Contents:
SafeTensors loader (direct into tpt-tensor)
ONNX importer (via tpt-crucible Catalyst → TPT-IR → tpt-tensor)
GGUF loader (via tpt-gpu model registry)
HuggingFace Hub client
PyTorch .pt / .bin converter (one-way, via Catalyst)
Export to SafeTensors / ONNX
Universal data format reader (CSV/JSON/Parquet/Arrow-IPC/HDF5) from tpt-io
5.5. tpt-runtime — The Unified Execution Orchestrator
Starting point: Elevates tpt-gpu-runtime into a cross-backend orchestrator (new work)
Responsibilities:
Unified kernel dispatch across CPU / WGPU / CUDA / ROCm / Metal / FPGA / Photonic / MCU
Asynchronous stream management (compute + copy stream overlap)
Memory pooling with liveness-aware buffer reuse (informed by tpt-compiler memory planning)
Pinned memory management for zero-copy host↔device transfers
Cross-device synchronization barriers
Integration with tpt-telos-uir-bridge for formal memory-bound proofs
6. The Language Runtime
The language runtime is the execution engine for TPT Script. It provides the dynamic value model, execution modes, and object model that make the language feel Python-like while maintaining Rust-level performance.
Starting point: tpt-rust6::tpt-script (Pythonic scripting layer — already implemented), adapted for Cobalt's tensor-first semantics.
6.1. Dynamic Value Model
The runtime Value enum represents all possible values in TPT Script. Tensors are first-class, not boxed through a generic object system.

pub enum Value {
    None,
    Bool(bool),
    Int(i64),
    Float(f64),
    Str(Arc<str>),
    List(Gc<RefCell<Vec<Value>>>),
    Dict(Gc<RefCell<HashMap<String, Value>>>),
    Tuple(Arc<[Value]>),
    Tensor(Tensor),              // Native, zero indirection
    Function(Arc<Function>),
    Module(Arc<Module>),
    Unit(Arc<UnitValue>),        // Compile-time unit-aware values
}

Key design decisions:
Tensor is a direct variant, not Box<dyn Any>. This eliminates runtime type checks and indirection for the most common operation.
Unit values carry dimensional metadata (meters, seconds, etc.) that the type checker validates at compile time.
Collections (List, Dict) use garbage-collected references for cyclic structure support.
Function and Module are reference-counted for sharing across the runtime.
6.2. Execution Modes
TPT Script supports three execution modes, selected per-function or per-expression:

pub enum ExecutionMode {
    /// REPL / notebook mode: interpret directly, no compilation
    /// Fast startup, slow execution, full introspection
    Eager,
    
    /// @compile decorator: trace execution into IR, optimize, cache
    /// Slow first call, fast subsequent calls, limited introspection
    Traced,
    
    /// Ahead-of-time compilation to native code
    /// Slow compilation, fastest execution, no introspection
    Compiled,
}

How they work:
Eager mode (default for REPL):
Parser → AST → interpreter
Each operation executes immediately
Full error messages with source locations
No optimization, no fusion
Used for exploration, debugging, small scripts
Traced mode (@compile decorator):
Parser → AST → tracer → IR graph → optimizer → cached compiled artifact
First call traces execution, builds IR, runs compiler passes
Subsequent calls execute the optimized graph
Limited introspection (can't print intermediate values without breaking the graph)
Used for training loops, hot paths, production inference
Compiled mode (future):
Parser → AST → compiler → native code (via Cranelift or LLVM)
No runtime overhead, but no dynamic behavior
Used for deployment to resource-constrained targets
6.3. Object Model
TPT Script's object model is minimal by design:

pub struct Module {
    pub name: String,
    pub attrs: HashMap<String, Value>,
    pub doc: Option<String>,
}

pub struct Function {
    pub name: String,
    pub params: Vec<Parameter>,
    pub body: AstNode,
    pub mode: ExecutionMode,
    pub compiled_cache: RwLock<Option<CompiledGraph>>,
}

pub struct Parameter {
    pub name: String,
    pub ty: Option<TypeAnnotation>,
    pub default: Option<Value>,
}

What's not in the object model:
No classes (use modules + functions instead)
No inheritance (use composition)
No metaclasses (no need)
No descriptors (too complex for the use case)
Why this matters: A minimal object model means the runtime is simple, fast, and easy to reason about. Most ML code doesn't need classes — it needs functions that operate on tensors.
6.4. Type System
TPT Script is statically typed with gradual typing:

pub enum Type {
    None,
    Bool,
    Int,
    Float,
    Str,
    Tensor { shape: ShapeInference, dtype: DType, device: Device },
    List(Box<Type>),
    Dict(Box<Type>, Box<Type>),
    Function { params: Vec<Type>, ret: Box<Type> },
    Unit(Dimension),
    Any,  // Escape hatch for dynamic code
}

Key features:
Tensor shape inference: The compiler tracks shapes through operations and rejects mismatches at compile time.
Unit checking: Dimensional analysis is enforced statically.
Gradual typing: You can annotate types where you want safety, leave them off where you want flexibility.
No runtime type checks: If it compiles, it's type-safe. No isinstance checks in the hot path.
6.5. Integration with the Stack
The language runtime integrates with the rest of the stack as follows:

tpt-gpu-script (parser, type checker)
    ↓
Language Runtime (Value enum, execution modes)
    ↓
tpt-tensor (tensor operations)
    ↓
tpt-autograd (gradient tracking)
    ↓
tpt-runtime (kernel dispatch)

The runtime is the bridge between the user-facing language and the underlying computational engine. It translates high-level operations into tensor ops, manages the autograd tape, and dispatches to the appropriate backend.
7. Tooling Architecture
The tooling layer provides the interactive development experience: REPL, notebooks, and IDE integration. This is what makes TPT Cobalt feel like a modern development environment, not just a compiler.
7.1. REPL (Read-Eval-Print Loop)
Starting point: tpt-gpu-script-cli (existing REPL implementation), enhanced with tensor-aware pretty-printing.

pub struct Repl {
    history: History,
    env: Environment,
    printer: TensorPrinter,
}

impl Repl {
    pub fn eval(&mut self, input: &str) -> Result<Value, Error> {
        let ast = parse(input)?;
        let value = self.env.eval(&ast)?;
        self.printer.print(&value);
        Ok(value)
    }
}

Features:
Line editing: Arrow keys, history, search (via rustyline)
Multi-line input: Detect incomplete expressions, allow continuation
Tensor pretty-printing: Show shape, dtype, device, requires_grad
Async execution: Long-running operations (training loops) don't block the REPL
Introspection: dir(), type(), help() work on all values
Magic commands: %time, %load, %save, %debug
Example session:

> x = randn(3, 4, device="cuda")
Tensor(shape=[3, 4], dtype=f32, device=cuda, requires_grad=false)

> y = x @ x.T
Tensor(shape=[3, 3], dtype=f32, device=cuda, requires_grad=false)

> y.mean()
Tensor(0.0123, dtype=f32, device=cuda)

pub struct LanguageServer {

    compiler: Compiler,
}

impl LanguageServer {
    pub fn on_completion(&self, pos: Position) -> Vec<CompletionItem> {
        // Tensor-aware completions: suggest valid operations based on shape/dtype
        let tensor_type = self.infer_type_at(pos)?;
        self.suggest_operations(&tensor_type)

        // Show tensor shape, dtype, device on hover

        // Shape mismatches, unit errors, type errors

8. System Layer
The system layer provides the low-level infrastructure: memory management, inter-process communication, and serialization. This is what makes TPT Cobalt performant and production-ready.
8.1. Memory Allocator
Starting point: tpt-gpu-runtime (existing 3-tier allocator), unified across all backends.

pub struct Allocator {
    slab: SlabAllocator,        // Fast, small allocations (< 1MB)
    buddy: BuddyAllocator,      // Medium, fragmented allocations (1MB - 1GB)
    fallback: SystemAllocator,  // Large, rare allocations (> 1GB)
}

impl Allocator {
    pub fn allocate(&mut self, size: usize) -> Result<Buffer, AllocError> {
        if size < SLAB_THRESHOLD {
            self.slab.allocate(size)
        } else if size < BUDDY_THRESHOLD {
            self.buddy.allocate(size)
        } else {
            self.fallback.allocate(size)
        }
    }
    
    pub fn deallocate(&mut self, buffer: Buffer) {
        // Route to the appropriate tier based on size
    }
}

Features:
Three-tier hierarchy:
Slab allocator: Pre-allocated blocks, O(1) allocation/deallocation, minimal fragmentation
Buddy allocator: Power-of-two blocks, O(log n) allocation, moderate fragmentation
System allocator: mmap / VirtualAlloc, O(n) allocation, no fragmentation
Memory pooling: Reuse buffers for tensors whose lifetimes don't overlap
Pinned memory: Page-locked host memory for zero-copy CPU↔GPU transfers
Device-aware: Separate allocators for CPU, GPU, FPGA, etc.
Thread-safe: Lock-free allocation for hot paths
Integration with tpt-runtime:
The runtime queries the compiler's memory planning pass to determine buffer lifetimes
Buffers are allocated from the pool and returned when no longer needed
Peak memory usage is tracked and reported
8.2. Inter-Process Communication (IPC)
TPT Cobalt supports sharing tensors across processes for distributed training and inference.

pub trait SharedTensor {
    fn share(&self) -> SharedMemoryHandle;
    fn from_handle(handle: SharedMemoryHandle) -> Self;
}

pub struct SharedMemoryHandle {
    id: String,
    size: usize,
    device: Device,
}

Features:
Shared memory: Tensors can be shared across processes via OS shared memory
Zero-copy: No data duplication, just handle passing
Cross-device: Share CPU tensors, GPU tensors, even FPGA buffers
Reference counting: Handles are reference-counted, memory is freed when last handle drops
Security: Handles are capability-based, can't be forged
Use cases:
Distributed training: Share model parameters across workers
Data loading: Preprocess data in separate processes, share with training loop
Inference serving: Load model once, serve multiple requests
Implementation:
Linux: shm_open + mmap
macOS: shm_open + mmap
Windows: CreateFileMapping + MapViewOfFile
GPU: CUDA IPC handles (cudaIpcGetMemHandle)

8.4. Streams & Synchronization
Modern hardware (GPUs, FPGAs) is asynchronous. The system layer manages streams and synchronization.

pub struct Stream {
    id: StreamId,
    device: Device,
    queue: CommandQueue,
}

impl Stream {
    pub fn submit(&mut self, kernel: Kernel) -> Result<(), SubmitError> {
        self.queue.submit(kernel)
    }
    
    pub fn synchronize(&mut self) -> Result<(), SyncError> {
        self.queue.synchronize()
    }
}

Features:
Multiple streams: Overlap compute and data transfers
Dependencies: Explicit dependencies between streams
Events: Synchronize across streams
Priority: High-priority streams preempt low-priority ones
Integration with tpt-runtime:
The runtime creates a default stream for each device
Users can create additional streams for parallelism
The autograd tape tracks stream dependencies to ensure correct execution order

10.1. Compile-Time Unit Safety
# TPT Script
let velocity = 10.0 * (meter / second)

Powered by tpt-math-units. No runtime overhead. No silent garbage.
10.2. Formally Verified Compilation
tpt-telos-uir-bridge consumes a compiled TPT-UIR graph and mathematically proves:
"For all possible input shapes within the declared bounds, every memory allocation in every scope fits within the target hardware's physical memory budget."
If the proof fails, it returns a concrete counterexample. No more silent OOM crashes in production.

11. Execution Flow: End-to-End
How a training step actually runs in TPT Cobalt:
Parse — tpt-gpu-script parses source into AST with tensor shape + unit inference.
Runtime — Language runtime creates Value objects, manages execution mode.
Trace — tpt-autograd records tensor ops into a reverse-mode tape.
Lower — Tape is converted to tpt-ir graph.
Verify — tpt-telos-uir-bridge proves memory bounds for the target device.
Optimize — tpt-gpu-compiler runs fusion, DCE, memory planning passes.
Dispatch — tpt-runtime routes kernels to the correct backend (CUDA/WGPU/FPGA/…).
Execute — Forward pass runs; activations saved for backward.
Backward — tpt-autograd replays VJPs in reverse, including through any tpt-physics or tpt-science ops in the graph.
Update — tpt-ml::optim::AdamW applies gradients to parameters.
Return — Loss scalar returned to the REPL/notebook.

13. What This Is NOT
To be explicit about scope:
Not a Python clone. TPT Script is Python-inspired, not Python-compatible. We do not replicate CPython semantics.
Not a PyTorch clone. We do not replicate PyTorch's dispatcher, autograd quirks, or eager/graph duality. We unify them.
Is a monorepo for Cobalt's purposes, without retiring the originals. The nine pillar repos are forked into tpt-cobalt as Cobalt's own optimized copies — not tracked as external dependencies, free to diverge. The tpt-solutions/* originals remain independently maintained products in their own right; they are not deprecated, and Cobalt's changes are not obligated to flow back into them. Anyone using tpt-fem or tpt-physics standalone keeps getting a maintained repo — just not necessarily the same internals Cobalt is running.
Not a research project. Every pillar is already built and tested. Cobalt is integration, not invention.
